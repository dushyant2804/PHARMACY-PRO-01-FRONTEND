PharmacyOS – Permanent Financial Register System (Complete Architecture Rewrite)

This is a major architectural change, not a feature addition.

The Daily Sales module must be permanently replaced with a new Financial Register system that is designed to remain the core financial module of PharmacyOS for many years.

Do not make temporary solutions, shortcuts, compatibility layers, duplicate pages, or quick fixes.

---

General Rules

1. Think like a senior software architect.

Before changing any code, understand how the entire backend and frontend currently work.

Preserve every existing feature unless this prompt explicitly replaces it.

Do not remove unrelated functionality.

---

2. This is a permanent replacement.

The Register module completely replaces the existing Daily Sales module.

After implementation:

- Remove Daily Sales page.
- Remove Daily Sales route.
- Remove Daily Sales navigation entry.
- Remove unused code related only to Daily Sales.
- Register becomes the only financial entry module.

Do not leave legacy code behind.

---

3. Financial integrity is the highest priority.

Never sacrifice correctness for convenience.

If an implementation decision could affect financial data integrity, stop and explain the trade-offs before making assumptions.

---

4. Single source of truth.

Every financial calculation must have one authoritative source.

Backend performs calculations.

Frontend displays backend results.

Never duplicate financial calculations between frontend and backend.

Avoid any situation where frontend totals and backend totals can become different.

---

---

Financial Year

Use Indian Financial Year.

Example:

FY 2026–27

starts

1 April 2026

ends

31 March 2027

Users never create financial years manually.

The system creates and manages them automatically.

---

Monthly Registers

Each Financial Year contains twelve monthly registers.

Example:

April 2026

May 2026

June 2026

July 2026

...

March 2027

These registers are automatic.

Users never create them.

---

Automatic Opening and Closing

Only the current month remains editable.

When a new month starts:

Automatically close the previous month.

Automatically open the new month.

No manual closing required.

No manual opening required.

---

Register Locking

Every previous month becomes read-only automatically.

Current month remains editable.

Future months remain unavailable until they begin.

Locking must be enforced on the backend.

Frontend locking alone is not acceptable.

---

Unlocking Closed Months

Closed months can only be edited after entering the existing Privacy Password.

Reuse the current Privacy Password system.

Do not create another password system.

Unlock should:

only unlock one month

be temporary

expire automatically

be audited

---

Audit Trail

Every edit made inside a closed register must record:

User

Date

Time

Previous value

New value

Reason if available

Nothing should silently change financial history.
